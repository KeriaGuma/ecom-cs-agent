# ECom-Bench：中文电商客服上的单 Agent 与多 Agent 对比

[ECom-Bench](https://github.com/XiaoduoAILab/ECom-Bench)（[论文](https://arxiv.org/abs/2507.05639)）是晓多 AI 发布的中文电商客服基准，在 τ-bench 的基础上改造，许可证为 Apache-2.0。

**场景和工具**：

- 场景是京东店铺客服，家电家居品类。政策里有京东 E 卡、价保、晒单返现、上门安装维修等真实业务；
- 21 个工具，用 MCP 协议提供：用户、订单、物流、商品、安装、故障码、赠品、配件、维修、优惠、识图，以及改单、退货、换货、E 卡、催单、开票、返现登记、预约服务；
- 工具把“查询”和“办理”合在一起。比如 `manage_order` 既能查订单，又能取消、修改订单和下单。

**任务和评分**：

- 53 个任务，每个由一位不同的标注员编写，用户画像很细（情绪、耐心、信任程度等）。**多意图非常密集**，一段对话常有 4～8 件事；
- 评分是“全对才得分”，三条都满足才算成功：
  1. 把标准答案的操作重放到原始数据上，和 Agent 改过的数据逐字节比对；
  2. 规定的查询工具都调用过，且参数完全一致；
  3. 回复里包含规定的关键词。

## 运行方式

代码在本目录，**不修改 ECom-Bench 的源码**。ECom-Bench 开源时清空了所有模型接口，这里在运行时注入：

| 项目 | 设置 |
| --- | --- |
| 代码版本 | ECom-Bench 固定在提交 `bc5018d`，使用上游单独的虚拟环境（pydantic 需固定为 2.11）。该环境保留上游自身依赖。 |
| 客服模型 | deepseek-flash，temperature=0（与本项目其他实验一致；ECom-Bench 默认 0.3），关闭思考模式 |
| 模拟用户 | deepseek-flash，保持 ECom-Bench 默认的 temperature=0.3 |
| 识图工具 | 原接口已清空，改接阿里云百炼的 qwen3.7-flash（[server/server.py](server/server.py)）。只替换模型调用，工具的提示词和参数不变 |
| API Key | 只从项目 `.env` 读取，不出现在命令行和结果文件里 |
| 启动 | [run.py](run.py) 支持 `--impl baseline`（上游原版复现）、`--impl single`（工程化单 Agent）或 `--impl team`（Supervisor 多 Agent 对照），以及 `--split dev/test` |

两种实现均保留异步 MCP 工具调用以及上游评分器所需的完整原始工具轨迹。新报告的 `usage_*.json` 用 `runtime` 记录运行时环境。

**排除的任务**：15 个任务依赖的图片链接已经失效（跳转到京东错误页，2026-11-10 检查），无论用什么模型都无法按原设计完成，所以排除，剩 38 题。因此**分数不能和论文直接比较**。

**划分**：ECom-Bench 没有官方划分。按固定随机种子分层划分（[split.json](split.json)）：能用的 3 个图片任务分 1 题进开发集、2 题进测试集；纯文本任务约 1/3 进开发集。最终**开发集 13 题，测试集 25 题**。划分在细看任务之前完成，测试集只跑一次（[test_runs.log](test_runs.log)）。

## 对比的三种实现

- **ECom-Bench 自带单 Agent**：`AgentLangChain`，即 LangGraph 的 ReAct Agent，加上全部 21 个工具和政策。除模型和温度外不做修改。注意它每轮只保留文字回复，**上一轮的工具结果不会带到下一轮**。
- **我们的多 Agent**（[ecom_team.py](ecom_team.py)）：结构和本项目 cs_agent 一致，“调度员统一规划，Worker 汇报”：
  - 只有前台（调度员）和用户对话。它没有业务工具，只能用 `delegate` 委派任务，外加转专员；
  - 三位专员按工具分工：订单与物流、售后与返现、商品与服务。专员不和用户说话，办完事把结论交回前台；
  - 需要用户确认的操作，专员先把明细写进汇报，前台向用户确认后再委派执行；
  - 每位专员都拿完整政策：政策章节之间互相引用，这是航空实验的教训。
- **我们的单 Agent**（[ecom_single.py](ecom_single.py)）：和多 Agent 共用所有与架构无关的工程手段，只是不拆分角色。
  - 工具和政策与自带单 Agent 完全相同；
  - **工作方式提示**：多个诉求逐件处理、按规则先确认再办、缺信息就问、不编造。和多 Agent 前台、专员的要求一一对应；
  - **“谎报完成”检查**：和多 Agent 相同，只是把“本轮没有委派”换成“本轮没有调用工具”；
  - **跨轮保留完整的工具调用和结果**。多 Agent 靠团队工作记录做到这一点，自带单 Agent 没有。

  它用来区分多 Agent 的提升到底来自架构，还是来自这些工程手段。

## 开发集（13 题 × 3 次）

下列开发集和测试集报告来自历史 LangGraph 实现。迁移到 Pi 后应先在开发集运行新版本，报告按运行时区分。

| 版本 | 改动 | pass^1 | pass^3 |
| --- | --- | --- | --- |
| 自带单 Agent | — | 38.5% | 23.1% |
| 多 Agent 第 1 轮 | — | 30.8% | 15.4% |
| 多 Agent 第 2 轮 | 每位专员都能查询订单 | 38.5% | 7.7% |
| 多 Agent 第 3 轮（冻结） | 加“谎报完成”检查 | 53.8% | 23.1% |
| 我们的单 Agent（冻结） | 只跑 1 轮，未调整 | **64.1%** | **53.8%** |

多 Agent 开发中发现的两个问题，都是多 Agent 特有的：

1. **工具粒度和分工冲突**。政策要求退货前先查订单，但查订单只能用 `manage_order`，它分给了订单专员。售后专员为了“查状态”，调用了 `manage_return`，而这个工具一调用就直接提交了退货。它还在汇报里说“未执行退货”。

   修法：`manage_order` 也给售后和商品专员，但职责里写明只用来查询。根源在于工具把读和写合在一起，按工具分工就没法把权限分开。
2. **前台谎报完成**。用户确认“两个订单都加急”后，前台没有委派任何专员，直接回复“已加急”。

   修法：代码检查。本轮没有委派、回复里却出现“已为您加急”“提交成功”这类完成说法时，先不发出去，提醒前台重新决定，最多一次。

## 测试集结果（25 题 × 3 次，每种实现只跑一次）

| | 自带单 Agent | **我们的单 Agent** | 我们的多 Agent |
| --- | --- | --- | --- |
| pass^1 | 42.7% | **69.3%** | 48.0% |
| pass^2 | 24.0% | **57.3%** | 30.7% |
| pass^3 | 16.0% | **48.0%** | 20.0% |
| 失败项（75 次中）：数据库 / 查询 / 关键词 | 36 / 9 / 0 | **19 / 6 / 0** | 34 / 11 / 0 |
| 每次模拟的客服 Token | **79659** | 90287 | 114814 |
| 每次模拟的客服模型调用 | 12.3 | **11.3** | 21.6 |
| 每轮回复延迟 p50 / p95 | **4.0s** / 9.1s | 4.2s / **8.9s** | 9.2s / 16.8s |

逐任务配对比较：

| 对比 | 差异 | 95% CI | 结论 |
| --- | --- | --- | --- |
| 我们的单 Agent − 自带单 Agent（**工程手段的作用**） | **+26.7%** | +13.3%～+41.3% | 显著 |
| 我们的多 Agent − 我们的单 Agent（**架构的作用**） | **−21.3%** | −36.0%～−5.3% | 显著 |
| 我们的多 Agent − 自带单 Agent | +5.3% | −13.3%～+24.0% | 不显著 |

**按任务复杂度拆分**（描述性分析，样本少，不做显著性结论）：

| 分组 | 题数 | 自带单 Agent | 我们的单 Agent | 我们的多 Agent |
| --- | --- | --- | --- | --- |
| 需要 1 位专员 | 10 | 40% | **73%** | 40% |
| 需要 2 位专员 | 11 | 55% | **73%** | 58% |
| 需要 3 位专员 | 4 | 17% | **50%** | 42% |
| 1～3 个意图 | 8 | 46% | **75%** | 42% |
| 4～5 个意图 | 13 | 41% | **64%** | 49% |
| 6 个以上意图 | 4 | 42% | **75%** | 58% |

“需要几位专员”按标准答案里的操作和查询工具归属统计。

**多 Agent 的“谎报完成”检查**：在 75 次模拟中，有 15 次触发，共 16 次。

### 评测纪律说明

- 测试集上，自带单 Agent 和多 Agent 先跑了一次。之后才决定加跑“我们的单 Agent”，所以测试集是第二次使用；
- 这个实现不是根据测试集的失败设计的，而是把多 Agent 里与架构无关的部分原样搬过来；
- 它在开发集上只跑 1 轮，没有任何调整就冻结了（[test_runs.log](test_runs.log)）。相比之下，多 Agent 在开发集上改了 3 轮。

## 结论

1. **提升来自工程手段，不来自架构**。只看多 Agent 和自带单 Agent 的对比（+5.3%），容易得出“多 Agent 在复杂任务上占优”的结论。加上同等工程水平的单 Agent 后，结论反过来了：
   - 工程手段带来 +26.7%，显著；
   - 拆成多 Agent 反而 −21.3%，显著。

   而且在每一档复杂度上，我们的单 Agent 都最好。
2. **多 Agent 的损耗来源**，开发和测试中都观察到：
   - 前台只看专员的汇报，细节在转述中丢失；
   - 需要确认的操作要在前台和专员之间来回一趟；
   - 前台会编造下游的执行结果，测试集上约五分之一的对话触发过检查；
   - 工具把读写合在一起，按工具分工就管不住权限。
3. **这些工程手段的价值**，就是自建项目里那些设计在公开基准上的验证：
   - 跨轮保留工具结果，对应本项目的【关键事实】和三层记忆；
   - 用代码兜住模型的谎报，对应本项目“关键判断交给代码”；
   - 明确的工作方式提示。

   三项各自贡献多少还没有拆开，可以再做一次消融实验。
4. **方法论上的教训**：比较架构时，基线必须是同等工程水平的实现，否则测到的是“工程手段”而不是“架构”。
