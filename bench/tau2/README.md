# τ²-bench 零售领域：单 Agent 与 Supervisor 多 Agent 对比

[τ²-bench](https://github.com/sierra-research/tau2-bench) 是客服 Agent 的公开基准，由 Sierra 发布。

**零售领域的内容**：

- 15 个工具：身份验证、查询、取消或修改待发货订单、已签收订单退换货、改默认地址、转人工；
- 政策要求：先验证身份，修改数据库前必须得到用户明确确认；
- 用模型扮演用户，对话结束后比对数据库状态，部分任务还会检查回复要点。

**官方划分**：训练集 74 个任务，测试集 40 个。我们用训练集开发，测试集只跑一次。

## 对比的两种架构

- **单 Agent**：τ²-bench 自带的 `llm_agent`，不做任何修改，作为官方基线。
- **Supervisor 多 Agent（中途交接版）**：[supervisor_agent.py](supervisor_agent.py)，Worker 的划分和本项目的多 Agent 一致，但 Worker 直接面对用户、对话中途互相转手。另一种结构（调度员汇报版，和本项目完全一致）见文末。

| Worker | 职责 | 政策章节 | 写工具 |
| --- | --- | --- | --- |
| account | 身份验证、查询、改默认地址 | 总则 + 领域基础 | modify_user_address |
| pending | 取消或修改待发货订单 | 总则 + 领域基础 + 取消和修改两章 | 4 个改单工具 |
| delivered | 已签收订单退换货 | 总则 + 领域基础 + 退货和换货两章 | 退货、换货 |

运行方式：

- 每收到一条用户消息，调度员决定交给哪个 Worker；工具结果回到发起调用的 Worker；
- 工具都由 τ²-bench 的环境执行，评估口径和单 Agent 完全一致；
- 调度员的模型调用不在 τ²-bench 记录的对话轨迹里，这部分 Token 会并入紧随其后的 Worker 消息，保证成本统计公平。

## 运行配置

| 项目 | 设置 |
| --- | --- |
| 模型 | 客服和扮演用户都用 deepseek-flash，temperature=0，关闭思考模式 |
| API Key | 只通过环境变量传入，结果文件里不会出现（见 [run.py](run.py)） |
| 回复要点判定 | τ²-bench 源码里写死为 OpenAI 的 `gpt-5.4-mini`，这里替换为 DeepSeek。**这是和官方设置的差异**，绝对分数不能和公开排行榜比较 |
| 代码版本 | τ²-bench 固定在提交 `033bf08`；冻结的多 Agent 代码哈希见 [test_runs.log](test_runs.log) |

## 在训练集上开发

另取 20 个训练任务，每个跑 1 次。只调多 Agent，官方单 Agent 不动。

| 版本 | 改动 | 通过 | 每任务客服 Token |
| --- | --- | --- | --- |
| 官方单 Agent | — | 18/20 | 78460 |
| 多 Agent 初版 | — | 15/20 | 61781 |
| 第 1 轮 | 加内部转交工具 `handoff_to_colleague` | 17/20 | 62801 |
| 第 2 轮 | 文字交接检测，交给调度员判断目标 | 16/20 | 72932 |
| 第 3 轮（冻结） | 从文字里直接识别交接目标，认不出再问调度员 | **18/20** | **61546** |

**开发中发现的主要问题：Worker 之间交接失败。** 这是多 Agent 系统的典型失败模式。Worker 知道某件事归同事管，但：

1. 手里没有转给同事的手段，只好调用 `transfer_to_human_agents`，把用户转给了真人客服；
2. 加了转交工具之后，又会**用文字宣布**“交给专员处理”，而不调用工具。模拟用户把这句话当成要被转接，直接结束了对话。

修法有三层：

- 给 Worker 一个内部转交工具，由 Agent 自己拦截，不交给环境执行；
- 提示词里写明转人工工具不能用来找同事；
- 代码兜底：检测到“交给同事”这类文字时先不发给用户，识别出目标同事后在内部换人重新生成。

只靠提示词约束不可靠，最后起决定作用的是代码兜底。

## 官方测试集结果

40 个任务，每个跑 3 次，多 Agent 代码在测试前冻结（哈希见 [test_runs.log](test_runs.log)），测试集只跑这一次。

| | 官方单 Agent（llm_agent） | Supervisor 多 Agent |
| --- | --- | --- |
| pass^1 | **90.0%** | 85.0% |
| pass^2 | **85.0%** | 80.0% |
| pass^3 | **80.0%** | 77.5% |
| 每次模拟的客服 Token | 76849 | **66709**（−13%） |
| 每次模拟耗时（中位数） | **30s** | 40s |

逐任务配对比较：多 Agent − 单 Agent = −5.0%，95% CI 为 −12.5%～+1.7%，**差异不显著**。多 Agent 更好 4 题，单 Agent 更好 7 题，持平 29 题。

**按任务类型拆分**：

| 任务类型 | 题数 | 官方单 Agent | 多 Agent |
| --- | --- | --- | --- |
| 只涉及一个写操作领域 | 29 | 90% | 90% |
| 只查询、不写数据 | 4 | 92% | 100% |
| **需要跨 Worker 协作**（取消或修改、退换货、改地址中有两类以上） | 7 | **90%** | **57%** |

**结论**：

- 只需要一个 Worker 的任务，两种架构完全打平；
- **多 Agent 的损失全部来自跨 Worker 交接**。即使开发阶段做了三层交接修复，同一段对话里需要换 Worker 的任务成功率仍然只有 57%；
- 多 Agent 的 Token 少 13%，因为每个 Worker 只看自己那部分政策；但速度慢约 1/3，因为多了调度员的调用。

**和本项目自建评测的对照**：在本项目的中文电商客服里，多 Agent 并不吃亏。原因是那边的调度员在第一次调度时就**规划好全部步骤**，各个 Worker 只把结论交回调度员汇总，Worker 之间不直接交接。而这里的 Worker 直接面对用户，需要在对话中途转手。

可见，**多 Agent 的成败很大程度取决于交接设计**。下一节用 τ²-bench 实测了“调度员统一规划和汇总”的模式。

## 第二种多 Agent：调度员汇报版

代码见 [plan_agent.py](plan_agent.py)，结构和本项目 cs_agent 的多 Agent 一致：

- 只有调度员和用户对话。调度员没有数据库工具，只能用 `delegate` 把任务委派给 Worker；
- Worker 不和用户说话，用自己的工具办事，最后一条文字消息就是交回调度员的汇报。Worker 能看到对话记录和团队工作记录（之前的委派、工具调用、结果和汇报）；
- 改数据库之前，Worker 先把拟执行的操作写进汇报，由调度员向用户确认。用户明确同意后，调度员再委派 Worker 执行；
- Worker 之间从不直接交接，跨领域的请求由调度员按顺序分别委派；
- Worker 的工具调用照常交给 τ²-bench 的环境执行。调度员和汇报这些内部调用的 Token，并入随后发出的那条消息。

**评测纪律**：

- 这个版本是看到上一节的测试分项结果后才决定做的，所以测试集是**第二次使用**；
- 开发只用训练集。在同样的 20 个训练任务上，第 1 版就是 18/20，和官方单 Agent 持平。2 个失败中，一个是三种 Agent 都失败的难题，另一个是模拟用户选的取消理由和标准答案不同；
- 因此第 1 版**没有任何调整，直接冻结**，测试集只跑一次（见 [test_runs.log](test_runs.log)）；
- 单 Agent 和中途交接版沿用上一节的测试结果，配置完全相同。

### 测试集结果（40 个任务 × 3 次）

| | 官方单 Agent | 中途交接版 | 调度员汇报版 |
| --- | --- | --- | --- |
| pass^1 | **90.0%** | 85.0% | 82.5% |
| pass^2 | **85.0%** | 80.0% | 74.2% |
| pass^3 | **80.0%** | 77.5% | 67.5% |
| 只涉及一个写操作领域（29 题） | **90%** | **90%** | 79% |
| 只查询、不写数据（4 题） | 92% | **100%** | **100%** |
| 需要跨 Worker 协作（7 题） | **90%** | 57% | 86% |
| 每次模拟的客服 Token | 76849 | **66709** | 92700（+21%） |
| 每次模拟耗时（中位数） | **30s** | 40s | 48s |

调度员汇报版和单 Agent 的逐任务配对比较：−7.5%，95% CI 为 −15.8%～0.0%，处在显著与不显著的边界上。多 Agent 更好 5 题，单 Agent 更好 11 题，持平 24 题。

### 失败类型

按“实际执行的写操作和标准答案差在哪里”分类：

| 失败类型 | 官方单 Agent | 中途交接版 | 调度员汇报版 |
| --- | --- | --- | --- |
| 没执行任何写操作 | 0 | **6** | 2 |
| 少做了操作 | 3 | 5 | 4 |
| 操作内容错误或多做 | 9 | 7 | 9 |
| **只错在支付方式** | 0 | 0 | **6** |
| 合计（120 次中） | 12 | 18 | 21 |

- **中途交接版**：典型失败是“没执行写操作”。Worker 宣布要转交，模拟用户以为要转人工，就结束了对话；
- **调度员汇报版**：交接问题基本消失，跨 Worker 任务从 57% 回到 86%。但出现了新问题：**写操作的确认被拆在两个 Agent 之间**。看了几段失败对话，有三种情形：
  1. Worker 拟的方案里没写支付方式，用户同意后才发现缺这项，只好再问一轮。这时模拟用户随口选了礼品卡（任务 60、61）；
  2. Worker 没问用户，直接把原支付方式写进方案（任务 74，用户本来会选信用卡）；
  3. 用户在选商品规格时顺带提了支付方式，调度员就当成用户已经确认，委派 Worker 执行。随后用户想改主意，已经来不及了（任务 71）。

  单 Agent 一个模型从头到尾掌握全部细节，确认时会把支付方式一起列出来，所以没有这类失败。
- 代价方面，调度员每轮都要多调用一次模型，Worker 还要读取工作记录，所以 Token 比单 Agent 多 21%，比中途交接版多 39%。

### 结论

1. **交接设计决定了失败出在哪里**。中途交接版输在对话被打断；调度员汇报版输在确认细节被转述丢失。两者都来自“信息在 Agent 之间传递”。
2. 只靠提示词让模型转述确认内容不可靠。本项目 cs_agent 的做法是：退款的确认和执行由代码把关（规则引擎 + 审批中断，审批通过后按结构化参数原样执行），所以自建评测中审批类任务是 100%。
3. 在这个规模（15 个工具、一段政策）上，单 Agent 的准确率、速度都是最好的。多 Agent 只有中途交接版在 Token 上更省，调度员汇报版没有成本优势。

**下一步可以验证的改进**：Worker 拟定的方案输出成结构化参数，并且要求方案必须包含支付方式；用户确认后，由代码原样执行这份参数，不再经过模型转述。零售测试集已经用过两次，这一改进要换新数据（如航空领域）来测。

## 第三种：结构化方案版（航空领域）

### 动机和做法

零售测试中，调度员汇报版有 6 次失败只错在支付方式（确认被拆在两个 Agent 之间，细节在转述中丢失）。改进方案（代码见 [team_agent.py](team_agent.py) 的 `team_struct`）：

- Worker 手里**没有写工具**，只能调用 `propose_action` 提交“工具名 + 完整参数”；
- 代码按该工具的参数定义校验，缺支付方式等必填项会被打回，校验通过后登记为方案 P1、P2……
- 调度员把方案给用户看，用户明确确认后调用 `execute_proposal`，由**代码把登记的参数原样**发给环境执行；
- 代码还会把关：方案必须先出现在调度员发给用户的消息之后，且用户回复过，才允许执行。

对照组 `team_relay` 是同一份代码的转述确认模式（等同于零售的调度员汇报版）。

### 为什么换成航空领域

这个改进是看了零售测试集的失败对话才设计的，再用零售测试集检验，等于用看过的题验证。航空领域的测试集（官方划分：训练 30 题、测试 20 题）此前完全没有使用过。

### 训练集开发（30 题 × 1 次）

| 版本 | 官方单 Agent | 转述确认 | 结构化方案 |
| --- | --- | --- | --- |
| 第 1 轮 | 22/30 | 18/30 | 18/30 |
| 第 2 轮：Worker 改拿完整政策 | — | 20/30 | **25/30** |

第 1 轮发现：航空政策的章节互相引用。保险的赔付范围（只赔健康和天气原因）、会员的免费行李额，都写在“订票”一章里，负责取消和改签的 Worker 拿不到，于是错批了取消，或者说“查不到行李费”。第 2 轮改为每个 Worker 都拿完整政策，职责只靠工具划分。第 2 轮后，结构化方案版剩下的 5 个失败单 Agent 也都失败，于是冻结（哈希见 [test_runs.log](test_runs.log)）。

另外，航空任务有“是否告知用户某条信息”的判定，默认用 OpenAI 的模型，这里同样换成 DeepSeek（[run.py](run.py) 自动传入 `--communicate-judge`）。

### 测试集结果（20 题 × 3 次，只跑一次）

| | 官方单 Agent | 转述确认 | 结构化方案 |
| --- | --- | --- | --- |
| pass^1 | **80.0%** | 78.3% | 73.3% |
| pass^2 | **75.0%** | 73.3% | 63.3% |
| pass^3 | **70.0%** | **70.0%** | 55.0% |
| 与单 Agent 的配对差异 | — | −1.7%（CI −11.7%～+8.3%，不显著） | **−6.7%（CI −13.3%～−1.7%，显著变差）** |
| 每次模拟的客服 Token | **69226** | 91794（+33%） | 95878（+38%） |
| 每次模拟耗时（中位数） | **29s** | 47s | 48s |

**训练集上最好的版本，到测试集上最差。** 训练集每题只跑 1 次，30 题的波动本来就大，又是在修改后挑出的结果，容易高估。这正说明测试集必须是没见过的。

### 失败类型（60 次中）

| 失败类型 | 官方单 Agent | 转述确认 | 结构化方案 |
| --- | --- | --- | --- |
| **不该写却写了（违反政策）** | 0 | 0 | **3** |
| 只错支付方式 | 1 | 1 | 1 |
| 没执行写操作 | 5 | 3 | 2 |
| 少做了操作 | 1 | 2 | 3 |
| 操作内容错误或多做 | 5 | 7 | 7 |
| 合计 | 12 | 13 | 16 |

- **零售上针对的那类失败，航空上几乎不存在**：三种 Agent 只错支付方式的都只有 1 次，改进没有发挥的空间；
- **结构化方案版多出一类新失败**：用户确认后，执行了政策不允许的操作。
  - 任务 13：把返程目的地从洛杉矶改成拉斯维加斯，可政策规定改签不能改目的地；
  - 任务 6：用户想给已有预订补买保险，Agent 给另订了一张带保险的新票；
  - 任务 2：不符合条件却发了补偿券。

  单 Agent 和转述确认版在这 3 题上都是 3/3。

### 结论

1. **代码保证了“确认什么就执行什么”，但没有保证“执行的东西合规”**。转述确认模式下，Worker 执行前会再按政策看一遍，相当于有两道检查；结构化方案模式下，政策判断只在提方案时做一次，之后代码原样执行，不再复查。另外，“提方案、等别人确认”的说法，可能让 Worker 在提方案时放松了把关。这两点是推测，没有单独验证。
2. 这和本项目 cs_agent 的设计正好对照：本项目的退款审批不仅由代码执行，**资格也由代码判断**（退款规则引擎），模型既不能决定退不退，也不能决定退多少。τ²-bench 的政策只有文本，工具接口不检查规则，结构化方案版只把“执行”交给了代码，“判断”仍留给模型。
3. 要真正发挥“代码把关”，需要把政策里的硬规则写成代码校验，比如改签不能改起终点、保险不能后补、取消资格。这相当于给 τ²-bench 写一个规则引擎，和本项目的做法一致，但这是针对具体领域的工程，不再是通用架构。
4. 在 τ²-bench 这种规模（15 个左右工具、一份政策）上，三次实验的结论一致：**官方单 Agent 最准、最快**。多 Agent 能做到持平（转述确认版），但 Token 多三成，速度慢六成。
